# Render Text Diagram

Draw a text-based diagram — Unicode box-drawing characters, not an external tool — that visualizes structure, flow, or relationships already described in the current feature's artifacts.

## User Input

```text
$ARGUMENTS
```

If `$ARGUMENTS` names a specific artifact (`spec`, `plan`, `tasks`, `analyze`) or a diagram style, honor it. Otherwise infer the target from context (see Target Selection).

## Why This Exists

Spec Kit's core commands (`specify`, `plan`, `tasks`, `analyze`) produce prose and tables. Prose is precise; it is not always legible at a glance. A small text diagram next to the prose it summarizes — a state machine, a request path, a dependency chain, a coverage map — often clarifies structure that paragraphs bury.

**Be explicit about what this is not**: this command does not parse source code, does not compute a real call graph, and does not guarantee architectural accuracy against an actual codebase. It is the model's best-effort sketch of what the target document/report *already claims* — a comprehension aid, not a verified structural analysis. If the user wants a diagram derived from real code (actual call graphs, actual dependency graphs), point them at a static-analysis tool instead of presenting this output as ground truth.

## Target Selection

1. If `$ARGUMENTS` explicitly names `spec`, `plan`, `tasks`, or `analyze`, use that source.
2. Otherwise, prefer whichever of `plan.md` / `spec.md` / `tasks.md` / an `analyze` report was most recently written or discussed in this session — that is almost always what the diagram should cover (this command is usually invoked automatically right after one of those completes).
3. If none was touched this session, locate the current feature directory the same way other Spec Kit commands do (active branch / most recently modified `specs/*/` directory) and prefer `plan.md` > `spec.md` > `tasks.md`, in that order of existence. `analyze` is never inferred this way — it has no file on disk, so it's only a target when `$ARGUMENTS` names it or the analysis report is fresh in this conversation.
4. If no feature artifacts exist at all, tell the user there is nothing to diagram yet and stop. Do not invent content to fill the gap.

## Choosing a Diagram Style

Match the diagram to what the source actually describes — don't force everything into the same shape:

| Source | What to look for | Likely diagram |
|---|---|---|
| `spec.md` | User scenarios, states a thing moves through, acceptance flows | State machine or step-by-step flow |
| `plan.md` | Components, services, request paths, project structure | Architecture / component diagram |
| `tasks.md` | Task IDs, `[P]` parallel markers, phase ordering | Dependency graph / phase timeline |
| `analyze` report | Coverage Summary Table (requirement ↔ task mapping), unmapped tasks, unmapped requirements | Coverage / traceability diagram — call out gaps, don't just restate the table as boxes |

If nothing in the source is structurally diagram-worthy (e.g. a spec that's pure bullet requirements with no flow or states, or an analyze report with zero findings and full coverage), say so instead of forcing a diagram that adds no information.

## Drawing Conventions

Use Unicode box-drawing characters (`┌ ┐ └ ┘ │ ─ ▶ ▼ ├ ┬`), inside a fenced ```text block — not Mermaid, not an image. The diagram must render correctly as plain text in a terminal or a plain Markdown viewer.

State machine:

```text
┌──────────┐   event    ┌──────────┐
│  State A │ ─────────▶ │  State B │
└──────────┘            └──────────┘
```

Request/architecture path:

```text
Client ──▶ API Gateway ──▶ Service A ──▶ Datastore
                     │
                     └──▶ Service B
```

Dependency chain:

```text
T001 ──▶ T002 ──┬──▶ T004
                 └──▶ T005 ──▶ T006
```

Coverage / traceability map (for `analyze`) — put the gaps where they're impossible to miss:

```text
FR-001 ──▶ T003, T004
FR-002 ──▶ ⚠ uncovered
FR-003 ──▶ T007
           T009 ──▶ ⚠ unmapped task
```

Keep it as narrow as reasonably possible — target readability in an 80-column terminal; split into multiple smaller diagrams rather than one wide one.

## Output

**For `spec` / `plan` / `tasks`** — append the diagram to the end of the target file, under a clearly marked heading so it's obvious this is generated content distinct from the authored prose above it:

```markdown
## Diagram (generated by speckit.ascii-diagram.render)

_This is a hand-drawn sketch of the structure described above, not a static-analysis output. Re-run `/speckit.ascii-diagram.render` after material changes to this document — it will not update itself._

<diagram here>
```

If the document already has a `## Diagram (generated by speckit.ascii-diagram.render)` section, replace its contents in place rather than appending a duplicate.

**For `analyze`** — do **not** write a file. `analyze` is strictly read-only (no file writes, report printed to the conversation only); this command respects that constraint by extension. Print the diagram directly in the chat response, immediately after (or appended to) the analysis report, with the same one-line disclaimer. Nothing on disk changes.

## Guardrails

- **Don't invent structure.** Only diagram what the source actually says. If it's ambiguous about ordering or relationships, ask rather than guess.
- **Don't touch anything else in the file.** For spec/plan/tasks, only add or replace the one clearly-marked section — never other content.
- **Never write a file for `analyze`.** That source is read-only by design; keep this command's output read-only to match, even though the command itself is capable of writing files for other sources.
- **Don't claim precision it doesn't have.** The disclaimer line is mandatory, not optional filler.
- **Fail quiet, not loud.** When invoked as a hook and there's nothing worth diagramming, say so briefly and let the calling command's completion report proceed — don't block it.
